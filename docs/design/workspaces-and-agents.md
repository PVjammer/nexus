# Workspaces and agents

*Workstream task-mgmt, 2026-11-18. **Proposed, not built.** It comes from the user's feedback on the onboarding build (hand-off, levels, done, a hotkey agent, pins, threads) and follows on from [work items and tasks](work-items-and-tasks.md).*

## The problem

- **The project chat does everything.** Today one project agent sets up the project, shapes work items and pairs with you, and a work item's workspace is just a pane that shares that chat. The conversation only grows. There is no level for a workstream: one piece of work with its own context.
- **"Hand to the agent" only changes the assignee.** Nothing does the work, and nothing comes back to you.
- **Small asks are costly.** "Add a task to project B" or "tidy this screen" from inside a workstream either goes into that workstream's conversation, which moves its context along, or means leaving the screen.
- **Done is just a status.** Nothing wraps the work up: the session, panes, follow-ups and report stay as they were.

## Decisions (proposed)

1. **Three levels:**
   - **Home** is the global view: what needs you, across every project. Nothing project-specific lives there.
   - **A project** is a workspace dedicated to that project, with its agent as the **orchestrator**.
   - **A workstream** is a workspace inside its project, one per work item you're working on, opened on demand. It has its own agent, conversation, panes, brief, done-when and report.

   A workstream is 1:1 with a work item for now. Several sessions on one item can later be threads (decision 11), not a fourth level.

   **Every work item in progress has a workstream.** Starting an item opens a new workstream, or resumes its old one, and parking puts it to sleep with its session kept. An idle workstream costs nothing: it makes no model calls until there's something to do. The in-progress limit caps how many there are.
2. **The orchestrator always knows its workstreams and can do anything in them.**
   - **Always in its prompt:** each workstream's one-line status (whose move it is, its next task, its last activity), regenerated every turn.
   - **On request** it can:
     - read a workstream's transcript;
     - open its workspace;
     - message its agent, the way foreman sends to a workstream;
     - work on its tasks and items directly.
   - **No refusing.** A request about one workstream that's asked of the orchestrator is never refused or bounced. All work can be managed from the orchestrator, if you want to work that way.
   - **Digging in is the agent's choice, through three tools.** It works the way a coding agent handles a large repo. The orchestrator picks the right tool and nothing is withheld:
     - **Look it up:** `ws_transcript` with a search term or a range of turns, returning matches or a window, never the whole conversation unasked. Every result says how much is left and how to get it ("turns 40-60 of 212; from=61 for more"), like reading a file by line range or grepping a repo.
     - **Ask a copy:** `ws_ask(question)` forks the workstream's session (pi `--fork`) and asks the copy, which already knows the work and answers in a few lines. The real workstream conversation doesn't move. This is the sub-agent for "where does it stand?" or "why did it pick Y?". A small model never has to parse a long transcript itself.
     - **Message the agent:** `ws_message` is for when the workstream's agent should *do* something. The message waits for that agent's turn to end. While it waits, an **Interrupt?** button lets you cut in; the orchestrator can ask for an interrupt, but only you press it.

     The fork needs a context window big enough for the workstream's session. Past that point, it uses the compacted session.
3. **Hard boundaries exist only for security and privacy**, not to separate agent roles. These are the boundaries:
   - secrets never reach an agent;
   - sensitive agents (email and other private domains) can't be read or messaged by other agents ([sensitive agents](sensitive-agents.md));
   - Nexus never writes to the user's project folders;
   - plugins are sandboxed;
   - system guardrails can't be lowered (backlog, 2026-11-18).

   Anything else an agent can do in one place, the orchestrator can do there too.
4. **"Since your last turn": every agent learns what changed while it wasn't looking.** This is the collaborative core: you and the agents work on the same things, so each agent starts its turn from what's true now. The note is short, generated by the core, and covers two kinds of change:
   - **Nexus changes:** tasks, items, done, parked, pins and layout, each with who made it (you, the orchestrator, a quick ask, another workstream).
   - **Project changes:** files edited, added or deleted, commits, branch switches and stash changes. They're found by comparing a snapshot of the repo taken at the end of the agent's last turn (HEAD, branch, `git status`, and the size and hash of each changed file) with its state now. Without git, a capped walk of modification times.

   **Who made each change, as precisely as the core can know it:**
   - **Another agent session in Nexus:** exact, labelled by session (for example "workstream *CSV export*" or "quick ask"). Every agent write goes through a core tool under that agent's token. Today no Nexus agent can write to a project folder, so these are always Nexus data: tasks, items, notes, wiki and panes.
   - **You, in Nexus:** exact for anything done in the UI.
   - **You, running an agent's proposed command:** a command an agent proposed and you ran from Nexus's terminal is labelled "you ran *workstream X*'s command". The files changing afterwards are then attributed to that command (by time, and marked as approximate).
   - **Outside Nexus:** every other change to the project folder, from your editor or from another tool or agent such as Claude Code or a foreman session. A commit adds what its metadata says: the author, and any `Co-Authored-By` trailer, so "commit by you with Claude (outside Nexus)". Uncommitted edits outside Nexus can't be attributed further. They're labelled "outside Nexus".
   - **When workstreams can write code** (a later design review), each one writes through Nexus into its own Nexus-owned copy, so those changes become exact too.

   The note is capped, for example "12 files changed in `internal/scan/` (3 deleted) · 2 commits on `auth-v2` · task 'Write the writer' marked done (you)". The full list or diff is one tool call away, through `project_changes`, which uses the same paging as decision 2.

   - **Secret-looking files** (`.env`, keys) show by name only, never by content.
   - **A change in the project** goes to every workstream in that project. A change to a workstream's own item or tasks is listed first.
   - **A message from the orchestrator** is the exception: it arrives as a message in the workstream's conversation (decision 2).
5. **"Hand to the agent" sends the task to its workstream's agent.**
   - The task card shows the agent working, with its live steps, and you can take the task back at any time.
   - It finishes in **In review**, with what the agent did.
   - The workstream's background mode replaces today's separate task runs ("Draft for a task agent").
6. **Done means closeout:**
   - **Your Done is final.** Pressing Done is the acknowledgement, so there's no popup: a toast with Undo instead.
   - **An agent can only claim done.** The work goes to In review, and you get a Needs you card ("Is CSV export done?") with each done-when check and the agent's evidence. Confirming it is your Done; "Not yet" sends your reason back to the agent.
   - **Done starts the closeout,** a process defined by a skill and run by the workstream's agent. The default skill:
     1. writes the workstream's report: what was done, the decisions, and what's left;
     2. turns what's left into proposals on the project's list, for you to tick;
     3. lists loose ends in the repo (unmerged branches, uncommitted files) as suggested commands or tasks, since Nexus never touches the repo itself;
     4. archives the session, the panes and the notes with the work item, then stops the agent.
   - **Afterwards:** the work item moves to Done, which is hidden from home and the board but can be found. The orchestrator's status line becomes a one-line summary of the report.
   - **Undo reopens everything,** because closeout archives and never deletes.
7. **Closeout is configurable, like foreman's landing.**
   - **Where it's defined:** the default is `skills/closeout`. A project can have its own version (for example "update the changelog" or "ask before archiving"), which you edit or ask an agent to edit, with the same review as any skill change.
   - **What can't be skipped:** the steps that must always happen (archive, never delete) are enforced in the core. Required steps can later become guardrails.
8. **Episodic agents for home and popups.** Home's agent, the quick agent and Eitri work in **episodes**:
   - **An episode ends** when its work is settled. Home's ends when the needs it raised are resolved and its changes are applied; Eitri's when you Keep or Roll back; a quick ask's when its receipt is final. You can also end one yourself.
   - **What happens to the history:** the conversation is saved to disk, in Nexus's data directory, as an episode with a one-line summary. The next episode starts fresh.
   - **What carries over:** the last few episode summaries are in the prompt, so "now do the same for project B" still works.
   - **Looking back:** a history search tool can pull any past episode back in.
   - **On screen,** a finished episode collapses behind a divider with its summary, and it can be reopened. You never lose what was said.
   - **Ending is deterministic.** The agent doesn't decide on its own that it's done: the core ends an episode when its needs are resolved and its changes are settled, and the agent can suggest an end with a one-line summary.
9. **The quick agent is home's agent, opened from anywhere.**
   - **Same agent:** the hotkey window and home's prompt are the same episodic agent. In the window, its context is your screen: the workspace you're in, its brief and tasks, and what you've selected.
   - **What it can do:** organizing tools across every project (work items, tasks, needs, reading other projects) and `ask_user`. It has no edit or shell tools, so it stays fast on small local models.
   - **What it never touches:** the orchestrator's or a workstream's conversation. Its changes reach those agents only through decision 4.
   - **When an ask turns into real work,** "Continue in the workstream" moves it there.
   - **Eitri shares the window and the hotkey.** The window organizes by default, and the hammer switches it to Eitri. Eitri stays a separate specialist with only layout tools, which keeps it reliable on small models.
10. **A project can be private.** This is Nexus's first data that belongs to you alone. The core enforces it, not the prompts.
    - **What changes:** a private project's work items, tasks, todos, workspaces and conversations are hidden from every agent outside it: home's agent, the quick agent, Eitri and other projects' agents.
    - **What agents still see:** that it exists, and counts, like "busy" on someone's calendar. For example: "1 private project · 2 items need you · something due Friday". So no agent tells you that you have nothing on, or sends you a needs count that doesn't add up.
      - **Dates:** due dates show as a day only, with no title and no project detail. That's the calendar's "busy 2-3pm": enough for home to plan your week honestly.
    - **What you see:** cross-project widgets (Needs you, Board, Work items) show private items in full, marked by a lock and a private colour.
    - **What's checked:** every way out of the wall. That means the tools (`work_items`, `needs_you`, `projects_list`, history search), what the quick agent sees of your screen (a private widget reaches it as "private: 3 items"), and what Eitri sees when you point (the widget's kind only).
    - **Its own agents are locked down.** They work inside the wall: they see the project and do its work, but they have **no egress**. That means no web tools, no messages to agents outside, and a local model only, since sending work to a remote provider is also a way out ([sensitive agents](sensitive-agents.md)).
    - **When a private workstream needs the outside world,** it uses a **throwaway agent**: one with egress but no workspace context. It gets only the question you, or the private agent, write for it. It has no project data and no history, and it is discarded after the run.
      - **What it returns** comes back as a proposal you see first, and it is marked as coming from outside: data, never instructions. This is the declassification problem from sensitive agents, in reverse.
      - **The details are to refine later.** Who writes the question, whether you see it before it leaves, and which tools it gets.
    - **Making a project private later:** past episodes from home and the quick agent may already mention it. Nexus offers to remove those mentions.
11. **Pins are for you, for now.** You can pin any message, yours or the agent's, to a strip at the top of the chat, so you can keep chatting without scrolling back. A pin doesn't change the agent's context (that could come later).
12. **Threads are on the backlog** (2026-11-18). A thread branches a conversation at any message, with the history up to that point. The main conversation doesn't move, and the thread can bring back a summary or be dropped. pi already has `--fork`. Threads share their plumbing with episodes (decision 8): both are side conversations that are saved and listed.

## The model

```
Project ─ orchestrator run p:<id>          sees: every workstream's status line (always),
   │                                              transcripts / workspaces / messages (on request)
   └─ Workstream w:<item>                    run w:<item> (own conversation; interactive or background)
        layout ws:<item> (panes)             brief, done-when, tasks (from the work item)
        status line (derived)                report (written at closeout)
        state: open | background | closed (archived with the item)

Episode (home, quick, eitri)               summary, started/ended, transcript file, changes made
Pin                                        conversation id, message id, pinned by you
```

## Build order

1. **Done and closeout** *(built 2026-11-18)*: the toast with Undo, the agent's claim of done that goes to review, and the closeout skill. Colour coding was built straight into the app rather than as a separate mock: whose move it is on cards, rows and Needs you, and an accent for each widget kind.
2. **Workstream workspaces:**
   - the `w:<item>` run and its workspace, opened for every item in progress;
   - the status lines in the orchestrator's prompt;
   - `ws_transcript`, `ws_ask`, and `ws_message` with Interrupt?;
   - "since your last turn", including changes made outside Nexus;
   - the real hand-off.

   *Built 2026-11-18.* It differs from the design in these ways, each a follow-up:
   - **`ws_ask` uses a reader over the saved conversation,** not a pi `--fork` of the session. It works with either agent loop, but it doesn't see raw tool results beyond what the transcript keeps.
   - **Closeout runs as its own short task agent** that reads the workstream's conversation with `ws_transcript`, rather than in the workstream agent itself.
   - **Panes:** a workstream shares the project's panes: its work item pane plus its own chat. A pane layout per workstream is not built yet.
   - **The change note:** these parts aren't built yet:
     - attributing changes to a command an agent proposed in the terminal;
     - the note for folders that aren't git repos;
     - keeping the turn marks across a restart.
3. **Episodes, and the quick agent:** home's agent becomes episodic, then the hotkey window shares Eitri's.

   *Built 2026-11-18.* Notes on what was built:
   - **When home's episode ends:** when nothing it raised waits on the user, *and* it called `episode_close` or the user comes back after 20 minutes. The tool result after a change reminds it, which made small models use `episode_close` in the eval.
   - **Eitri's episode** ends at Keep, at Roll back, or when a small change goes live.
   - **Not built yet:**
     - Undo on the quick window's receipt (it lists what was done);
     - removing mentions of a project from past episodes when it's made private.
4. **Private projects:**
   - the wall in the core, with a test for each way out;
   - the "busy" view for agents;
   - the lock and colour in widgets.

   It can go earlier: it doesn't depend on workstreams.

   *Built 2026-11-18.* How it works:
   - **The checks:** every tool call checks its arguments, and something private gets the same answer as something that doesn't exist. Tools that list across projects skip private ones and add the "busy" line. As a last line of defence, the core scrubs any line of a tool result or context that still names a private item, task, path or project.
   - **The test:** `TestPrivateProjectWall` calls every tool of every outside agent with arguments aimed at the private project.
   - **Remote loops:** a private project's agents refuse a remote loop (Claude Code).
   - **Not built yet:**
     - throwaway agents with internet access (there are no web tools yet);
     - checking that a pi model is really local.
5. **Pins** (they're cheap, so they can go earlier). *Built 2026-11-18:* they're yours only and are stored in Nexus.
6. **Threads** (backlog).

Each step ships with its skills, its `TestSkillExamples` examples and eval cases, as for the rest of Nexus.

## Open questions

*Answered 2026-11-18:*
- **"Busy":** shows counts and day-only due dates.
- **Private projects:** they have locked-down agents, plus throwaway agents for egress.
- **Project changes:** for now they go to every workstream in the project, with the workstream's own changes listed first. This is the easiest to build and try.

1. **Should each workstream get its own working copy (a git worktree) to write code in?** Today Nexus's agents are read-only on your project: they write only Nexus's own data, and you run anything in the repo. A Nexus-owned worktree per workstream would give it room to write code, with no clashes between workstreams and every change exactly attributed. It is also the point where "never write to the user's project folders" needs a careful definition. **Next design review, after trying the build.**
2. **Throwaway agents:** who writes the question, whether you see it before it leaves, and which tools it gets.
